# Инструкции для агентов

## Язык проекта

Русский — основной язык MsgHub.

На русском должны быть:

- сообщения пользователю и оператору;
- логи и диагностический вывод;
- сообщения CLI и `--help`;
- комментарии и docstring в собственном коде;
- README и документация;
- Issues, описания PR и commit messages;
- тексты ошибок, предупреждений и эксплуатационных инструкций.

Идентификаторы в коде, имена полей машинных форматов, названия внешних API и иные элементы совместимости могут оставаться на английском. Не переводить протокольные поля ценой несовместимости или неоднозначности.

## Источник истины

Для фактического состояния проекта использовать текущий GitHub `main`, актуальный Issue/PR и файлы репозитория. Не доверять старым SHA, описаниям в handoff или прежним экспериментам без read-back.

Для задач ChatGPT Web сначала применяется `github_project_bootstrap.md`, затем runtime bundle `dist/projects/dilukhin__msghub.md` из `dilukhin/github-connector-knowledge`.

## Границы архитектуры

1. Ядро MsgHub платформонезависимо. Объекты Telegram, WhatsApp, VK и MAX не должны становиться моделью ядра.
2. Все платформы подключаются через адаптеры и каноническую модель событий.
3. Не создавать попарные маршрутизаторы вида `Telegram -> WhatsApp`; маршрутизация идёт через `LogicalRoom` и `Endpoint`.
4. Входящее событие и связанные `Delivery` должны быть долговечно записаны до признания входящего события принятым.
5. Защита от циклов, дедупликация и `MessageLink` должны переживать перезапуск.
6. `uncertain` означает неизвестность факта удалённого принятия сообщения. Не превращать его в обычный автоматический retry без reconciliation или явно принятой политики.
7. SQLite/WAL — исходное долговременное хранилище v0.1. Не вводить Redis, RabbitMQ, Kafka, PostgreSQL и другие обязательные службы без измеренной необходимости.
8. Мультимедиа — ограниченное временное состояние доставки, а не постоянный архив.
9. WhatsApp Web-совместимый транспорт считать заменяемой зависимостью повышенного риска и изолировать от relay core отдельным процессом/зоной отказа.
10. Целевая среда v0.1 — небольшая Ubuntu VPS порядка 1–2 vCPU, 1–2 GiB RAM и около 20 GiB SSD.

До завершения Issue #2 не фиксировать язык реализации, конкретный IPC и библиотеку WhatsApp как необратимое архитектурное решение.

## Секреты и приватность

Никогда не публиковать и не выводить в обычные логи:

- Telegram/WhatsApp/VK/MAX tokens;
- cookies;
- private keys;
- pairing/session material;
- QR/pairing credentials;
- базы runtime-сообщений;
- media cache;
- содержимое приватных сообщений и вложений, если оно не требуется для специально включённой диагностики.

Диагностика по умолчанию должна работать с идентификаторами, размерами, состояниями и кодами ошибок, а не с приватным payload.

## Работа по задачам

- Перед изменением прочитать Issue и затронутые контракты.
- Не расширять scope без отдельного решения.
- Значимые архитектурные решения фиксировать в документации/ADR, а не только в коде или обсуждении.
- Для новой функциональности добавлять автоматизированные проверки соответствующего уровня.
- Failure/restart/retry сценарии считать частью функциональности, а не необязательными edge cases.
- После записи во внешнее состояние проверять фактический результат read-back.

## GitHub

В ChatGPT Web GitHub Connector — первичный и штатный remote-транспорт. Не выполнять пробные `git`/`gh` remote-команды. Для многофайловых изменений через Connector использовать `blob -> tree -> commit -> ref`.

`main` не изменять напрямую при обычной разработке. Использовать task-ветку `agent/...`, PR, проверки и read-back после merge.
